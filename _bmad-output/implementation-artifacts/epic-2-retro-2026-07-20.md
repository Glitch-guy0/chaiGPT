## What Went Well ✅

### 1. **Review Process Caught Critical Bugs Before They Reached Production**

**Finding:** 12 HIGH-severity bugs were found during adversarial code review. Every single story that had HIGH bugs had them fixed before moving to the next story. The sequential implement→review cycle proved highly effective.

**Evidence:**
- Story 2.1: Dockerfile would fail to build (`output: "standalone"` missing), volume cleanup silently failing (wrong volume name), container hostnames wrong for production
- Story 2.3: Every authenticated user could access every other user's conversations (userId never used for scoping), auth failures returned 500 instead of 401, env file was gitignored
- Story 2.6: Compose profile didn't match CI invocation, DB had no tables after reset, auth state never created, wrong env vars for container networking

**Team Feedback:**
- **Charlie (Senior Dev):** "12 HIGH bugs caught in review is a lot. But that's the point — find them in review, not in production."
- **Dana (QA Engineer):** "The userId scoping miss in Story 2.3 was the scariest. That's a data leak that would've been catastrophic."
- **Amelia (Developer):** "Sequential implement→review on the same story before moving to the next was key. Each story's review findings informed the next story's implementation."

**Impact:** All 12 HIGH bugs fixed before any production deployment. The review discipline prevented data leaks, broken builds, and silent failures.

## What Didn't Go Well / Learning Opportunities ⚠️

### 1. **E2E Implementation Had the Most Review Findings — By Far**

**Finding:** Story 2.6 had 6 HIGH and 7 MEDIUM findings — more than all other stories combined. The complexity of orchestrating Docker Compose, Playwright, Clerk auth, DB resets, and CI integration created many failure modes.

**Root Cause:** E2E is inherently more complex than any single component story. It touches the entire stack: Docker networking, Postgres migrations, Playwright configuration, Clerk auth flows, file paths, CI secrets management.

**Evidence:**
- Compose profile never activated in CI (H2)
- DB tables never created after schema reset (H5)
- Auth storage state never persisted (H3)
- Container env vars didn't match app's expectations (H4)
- File paths resolved incorrectly between CWD and fixture locations (H6)

**Lesson:** E2E orchestration stories need extra scrutiny during implementation. Consider a pre-review checklist for Docker Compose networking, path resolution, and CI environment expectations.

---

### 2. **Authentication Security Bug Was Only Caught in Review**

**Finding:** The HIGHEST severity finding across the entire epic — Story 2.3's route handlers captured `userId` via `auth()` but never used it for query scoping. Any authenticated user could read, modify, or delete any other user's conversations.

**Evidence:**
- `src/app/api/conversations/route.ts` — `GET` returned ALL conversations, not filtered by `userId`
- `src/app/api/conversations/[id]/route.ts` — `GET` returned conversation by ID without verifying ownership
- `src/app/api/chat/route.ts` — no userId scoping on message queries

**Root Cause:** The implementation agent focused on getting auth() working (calling it, capturing userId) but didn't connect that value to the query layer. The "obvious" security boundary was assumed rather than implemented.

**Lesson:** Auth implementations need explicit checklist items: "For every route handler, verify that userId is used in EVERY database query." This is a pattern that should be in the story template for any auth-related story.

---

### 3. **Documentation Gap from Epic 1 Persists**

**Finding:** The 3 documentation action items from Epic 1's retrospective (project-context.md update, placeholder pattern doc, onboarding reference) were not addressed during Epic 2. Multiple story dev notes flagged the missing project-context.md as a source of confusion.

**Evidence:**
- Every Epic 2 story's Dev Notes mentioned: "Conflict flag: project-context.md is silent on backend/TypeORM concerns"
- Story 2.4 Dev Notes explicitly noted the middleware path discrepancy between `01-package.md` (`src/app/middleware.ts`) and actual Next.js requirement (`src/middleware.ts`)
- No documentation updates were made during Epic 2 execution

**Root Cause:** The Epic 2 stories were focused on implementation, and no story had "update docs" as an acceptance criterion. The action items from Epic 1 retro fell through the cracks.

**Lesson:** Documentation action items from retrospectives should be assigned to specific stories in the current or next epic. Consider adding a "documentation" task to the first story of each epic to address pending retrospective actions.

---

### 4. **Stories Left in "review" — No Done Transition**

**Finding:** All 6 stories are in "review" status, not "done." The sprint-status.yaml shows Epic 2 as "in-progress" rather than "done." The retrospective is running before the formal done-signoff.

**Root Cause:** The process defined story status transitions as: ready-for-dev → in-progress → review → done. The review step is complete for all stories (with fixes applied), but the final "done" transition requires manual signoff or a final check.

**Lesson:** Define the done-transition criteria. Options: (a) after code-review findings are resolved, move to done; (b) run a final validation epic-level check; (c) make the review agent also responsible for the done transition.

## Key Insights & Lessons Learned

### 1. **Adversarial Review Is Non-Negotiable for Auth & Security**

12 HIGH bugs found across 6 stories. The userId scoping bug in particular was a data leak that would have been catastrophic in production. Every auth-related story must go through adversarial review before deployment. This is a hard rule going forward.

### 2. **E2E Complexity Requires Pre-Review Checklist**

E2E stories touch Docker Compose, Playwright config, CI, env vars, file paths, auth mocking, and database orchestration. The volume of failure modes is higher than any other story type. Create a pre-review checklist for E2E stories:
- [ ] Docker Compose networking — container-to-container hostnames match app config
- [ ] CI profile/gate matches compose invocation
- [ ] DB reset produces usable tables (migrations or sync runs)
- [ ] Auth state is actually created and persisted
- [ ] File paths resolve correctly from CWD at test runtime
- [ ] API key dependencies are gracefully skipped, not failing

### 3. **Scope Discipline Remains Strong**

Following Epic 1's example, Epic 2 maintained strict story boundaries. No story overreached. The explicit "in scope / out of scope" guidance in story files was consistently followed. This pattern should continue for all future epics.

### 4. **Documentation Debt Compounds Rapidly**

Three action items from Epic 1's retro went unaddressed. Two epics in, the project-context.md is still frontend-only, and key architectural decisions are undocumented. This creates onboarding friction and risks misalignment as the team grows. Address documentation debt in Epic 3's first story.

### 5. **Sequential Implement→Review Cycle Is Effective**

Each story followed the pattern: implement → code review → fix → next story. This prevented bugs from accumulating across stories and ensured each story's foundation was solid before the next one built on it. Continue this pattern for Epics 3-7.
