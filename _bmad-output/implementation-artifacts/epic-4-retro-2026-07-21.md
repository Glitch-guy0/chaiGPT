## What Went Well ✅

### 1. Adversarial Code Review Caught Critical Corruption
The Blind/Edge-Case/Acceptance review layers caught a CRITICAL bug that 93 passing unit tests missed: `branch()` reuses message PKs, so `messageRepo.save(copy)` **mutates the source conversation's rows** instead of forking, and would PK-collide on Postgres. This validates the review-as-hard-gate process established in E3.

### 2. Test-First Discipline Held
Every E4 story was implemented test-first (red → green → refactor). Test count grew 93 → 101 → 106 across the 3 stories; coverage stayed above the 80% gate.

### 3. Clean Layered Architecture Preserved
Branching extended E3's `MessageRepository` / `ConversationRepository` without circular deps. `regenerate` (4.3) reused 3.6's `createStream()` with zero new streaming logic — the E3 shared-pipeline investment paid off again.

### 4. Scope Discipline Maintained
4.1/4.2/4.3 stayed within boundaries. No UI changes (correctly deferred to E6). Route handlers wired (`/branch`, edit, regenerate) without bleeding into service logic.

## What Didn't Go Well / Learning Opportunities ⚠️

### 1. CRITICAL — `branch()` Corrupts the Source Conversation (4.1)
`conversation.repository.ts:55-68` copies messages reusing `id: m.id`, then `messageRepo.save(copy)`. TypeORM `save` upserts by primary key — the existing source rows get their `conversationId` overwritten to the new branch. The source **loses its messages**; on Postgres the insert would throw a PK violation.
- **Root cause:** treating a shared `messages` table as copy-on-write without generating fresh ids.
- **Why tests missed it:** `conversation.repository.test.ts` seeds non-uuid ids and only asserts the branch result — the source mutation is invisible. Classic E3-predicted blind spot.
- **Fix:** generate fresh uuid per copied message, build `oldId→newId` map, remap `parentId`; preserve `createdAt`/`updatedAt`; wrap create+copy+`lastMessageId` update in `ds.transaction`. Revise spec AC#7 ("preserve original id") — it's incompatible with a true fork.

### 2. HIGH — `findById` Not Scoped by `conversationId` (4.2/4.3)
`message.repository.ts:27` queries `where:{id,userId}` — no conversation filter. Because 4.1 copies reuse ids across conversations, `findById(conv.lastMessageId, userId)` can return the *foreign branch's copy*. This is load-bearing in 4.2's `resolveTargetUserMessage` and 4.3's `regenerate` chain walk.
- **Fix:** add `findByIdInConversation(id, conversationId, userId)` and scope both call sites.

### 3. HIGH — 4.3 Null-Parent Fallback Pollutes Branch History
`message.repository.ts:63` + `chat.service.ts:210`: if a regenerated message has `parentId === null` inside a branched conversation, it falls back to `findByConversation`, returning **all** sibling branches — violating AC#2 (ancestor-only history).
- **Fix:** dispatch on `conversation.rootConversationId`, not on `parentId` nullness; or filter the fallback to the active lineage.

### 4. HIGH — Non-Atomic Regenerate Status Gate (4.3)
`chat.service.ts:204` status-check → `updateStatus` isn't atomic. Two concurrent calls both pass the `stopped` gate, both stream, last-write-wins.
- **Fix:** conditional update (`WHERE status='stopped'`), reject if `affected === 0`.

### 5. MEDIUM — Determinism Gaps
4.2 `findLatestSibling`/`findSiblingsByParentId` order only by `createdAt` — ties on identical timestamps make sibling selection nondeterministic. Add secondary `id` tiebreak. 4.2 `target.parentId!` non-null assertion misfires on root/fallback targets.

### 6. MEDIUM — 4.3 Chain Includes the Regenerated Message
`findMessageChain` starts the walk at `fromMessageId`, so the stopped assistant's stale content becomes the final history turn sent to the AI. AC#2 says *ancestor* messages. Start the walk at `start.parentId`.

### 7. LOW — Testing Infrastructure Gaps
No transaction around 4.2 guards+save (concurrent edit race). 4.3 `>500` truncation silently discards the ROOT with no log (unlike the orphan path). All fixable, but all were *unit-masked*.

## Key Insights & Lessons Learned

### 1. The Predicted Risk Is the Real Risk — Act on Retro Actions Before the Epic
Epic 3's retro named branch-aware query correctness as E4's top risk and assigned 3 "Before E4" actions to blunt it. They were skipped. The exact failure happened. **A retrospective that produces unactioned action items is decorative.** Action items with "before next epic" deadlines must be a gate, not a suggestion.

### 2. Unit Tests with Mocked Repos Are a False Comfort
Across E3 and E4, every CRITICAL/HIGH "silent" bug (E3: extracted text discarded, assets orphaned; E4: source corruption, cross-branch id bleed) passed green unit suites because tests feed the impl exactly what it expects. **Only real Postgres integration tests would have caught these.** E3 Action 4 (integration suite) is now 2 epics overdue and its absence directly caused E4's escapes.

### 3. Shared `messages` Table + Copy-with-Same-ID Is Inherently Fragile
Branching design reuses message ids across conversations. This makes every `findById`/chain walk ambiguous unless strictly scoped. The safer design (fresh ids + explicit lineage via `rootConversationId` + `parentId`) should be adopted in the fix pass; it also removes the Postgres PK-collision hazard.

### 4. Adversarial Review Is the Only Reliable Correctness Gate
TypeScript + ESLint would catch ~15% of findings (style). They catch **zero** semantic bugs. The 4.1 corruption, 4.3 null-parent pollution, and 4.2 tie-break are all invisible to the type system. Maintain review as a hard gate — but pair it with integration tests so reviews stop spending cycles on bugs tooling should have caught.

### 5. Documentation Debt Is Now Structural
4 epics of `project-context.md` / onboarding / placeholder-pattern debt. New stories (and review agents) must reverse-engineer architecture from planning artifacts each time. This slows every epic and degrades AI-context quality.

## Conclusion

Epic 4 implemented the full branching feature set and grew the test suite, but the adversarial reviews exposed that the foundation is not yet correct: `branch()` corrupts the source conversation, message lookups are not conversation-scoped, and regenerate has a history-pollution and concurrency hazard. Every one of these was predicted by Epic 3's retro, whose preventive actions were never executed.

The headline lesson: **a retrospective is only valuable if its "before next epic" actions are enforced as gates.** Epic 4's escapes are a direct consequence of unactioned retro commitments, not of insufficient review.
