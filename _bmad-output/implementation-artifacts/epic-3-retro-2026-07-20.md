## What Went Well ✅

### 1. **Sequential Implement→Review Cycle Maintained Quality**

Every story followed implement → code review → fix → next story. This prevented bugs from cascading between stories. The shared `createStream()` refactoring in 3.3 was validated before 3.6 built regenerate on top of it.

**Evidence:**
- Story 3.3 extracted `createStream()` as a shared helper — 3.6 reused it directly, zero refactoring needed
- Story 3.4's `OpenAiProvider` validation pattern (fail-closed API key check) was validated in isolation before ChatService depended on it
- Story 3.7's `splitContent()` was unit-tested in isolation before integration with `ChatService.send()`

**Impact:** No regressions across the 7-story chain. Each story landed on a validated foundation.

### 3. **Code Review Found Issues the Implementer Missed**

Every review layer (Blind Hunter, Edge Case Hunter, Acceptance Auditor) found actionable issues.

**Notable finds:**
- Story 3.3: Cancel handler was emitting SSE without event type — client couldn't distinguish cancel from completion
- Story 3.3: RAG context config was hardcoded dead code instead of `undefined` params
- Story 3.6: Wrong HTTP status (500 vs 400) for invalid message status — `try/catch` wrapped the guard
- Story 3.6: Missing `X-Accel-Buffering: no` header on SSE route — streaming would be buffered by nginx
- Story 3.7: Extracted text silently discarded — `for (const part of split.extracted)` stored nothing
- Story 3.7: No `assetIds` column on Message entity — created asset had no link back to the message

**Impact:** All review findings fixed before "done" transition. Zero bugs escaped to the next epic.

## What Didn't Go Well / Learning Opportunities ⚠️

### 1. **Code Review Blockers Found in Final Story (3.7)**

3 BLOCKERs in Story 3.7 were found during code review — all from the implementation agent not connecting the dots between asset creation and message persistence.

**Root Cause:** The implementation agent created the `splitContent()` utility and added the asset-creation loop in `ChatService.send()`, but never saved the extracted `part` content to the Asset entity's `text` column, and never linked the created asset IDs back to the user message's `assetIds` column. The asset was orphaned from the message it belonged to.

**Lesson:** Cross-cutting integration points (message ↔ asset, content ↔ reference) need explicit AC-level verification. If a story touches two entities that must be linked, the AC should specify the link mechanism.

**Prevention:** Add a "link check" to code review template: "For every newly created/updated entity, verify all references to other entities are persisted."

### 3. **No E2E Verification for Epic 3 Features**

All 81 tests are unit-level with mocked externals. No integration or E2E tests verify that the full stack (route handler → service → repository → Postgres) works end-to-end for the new streaming, editing, and regenerate flows.

**Evidence:**
- SSE streaming is tested with mocked `AiProvider` — no real streaming verification
- Edit-latest is tested with mocked `MessageRepository` — no real DB update verification
- Asset creation in 3.7 is tested with mocked `AssetRepository` — no real persistence verification

**Root Cause:** Epic 2's Playwright harness was designed for browser-level E2E, not service-level integration. There's no "integration test" layer between unit tests and E2E.

**Recommendation:** Consider adding a lightweight service-level integration test suite that exercises real Postgres (via disposable testcontainers or Docker) for the critical paths: send→stream→complete, edit→persist, regenerate→overwrite.

---

### 4. **Small Inconsistencies Slip Through Without Automation**

Several review findings were style/naming issues detectable by lint or typecheck rules:
- TS2564 `!` non-null assertions (3.1)
- Mixed named/default imports (3.2)
- Unused Zod `.catch()` (3.5)
- Wrong HTTP status in `try/catch` (3.6)

**Evidence:** 3 of the ~20 review findings would have been caught by stricter TypeScript config (e.g., `strictPropertyInitialization`) or ESLint rules (e.g., `no-unused-vars`, `import/no-named-as-default`).

**Recommendation:** Tighten the TypeScript `tsconfig.json` and add ESLint rules to catch these automatically. Review time spent on style issues is wasted — let the tooling catch them.

---

### 5. **Missing SSE Response Header Not Caught by Acceptance Review**

Story 3.6's acceptance auditor missed the missing `X-Accel-Buffering: no` header requirement — it was only caught by the Edge Case Hunter layer.

**Evidence:** The Acceptance Auditor verified AC compliance against the story file, but SSE buffering behavior (nginx/proxy-level) was not specified in any AC. The Edge Case Hunter identified that nginx would buffer SSE output, breaking progressive streaming.

**Lesson:** SSE-specific concerns (response headers, framing, connection management) should be documented in the story ACs for any SSE-related story, not left to reviewer intuition.

## Key Insights & Lessons Learned

### 1. **Shared Pipelines Prevent Duplication — But Must Be Extracted Early**

`createStream()` was extracted in Story 3.3 and reused in 3.6. If 3.3 had not factored out the shared logic, 3.6 would have duplicated it — doubling the bug surface.

**Action:** When a story's implementation reveals a natural shared abstraction, extract it proactively, not reactively. This applies to RAG context retrieval (used by both send and regenerate) and asset-to-message linking (used by both the composer and any future upload flow).

### 2. **Code Review BLOCKERs Cluster in "Connective" Stories**

Stories that touch multiple services/entities (3.3 touches ChatService + MessageRepository + AiProvider; 3.7 touches ChatService + AssetRepository + Message entity) generate more review findings than single-entity stories.

**Action:** Allocate more review time for connective stories. Consider adding a "cross-contract verification" step: "Ensure all entities touched by this story have their relationships persisted correctly."

### 3. **Documentation Debt Compounds Exponentially**

After 3 epics with unaddressed documentation actions, the project-context.md is now 3 versions behind the actual architecture. This directly impacts onboarding, code review (reviewers must infer architecture from planning artifacts), and AI context quality.

**Action:** Treat documentation as a first-class deliverable. Add a documentation task to the first story of Epic 4, or create a dedicated "docs catch-up" story.

### 4. **Two-Thirds of Review Findings Were "Silent" Bugs**

Findings like "extracted text never stored" (3.7), "SSE cancel event missing event type" (3.3), and "X-Accel-Buffering missing" (3.6) don't produce TypeScript errors — they're semantic bugs. TypeScript cannot catch them. This validates the adversarial review approach.

**Action:** Maintain adversarial code review as a hard gating step. Do not rely solely on type checking or linting for correctness.

### 5. **Test-First Discipline Reduced Rework**

Stories that followed test-first (write test, implement until test passes) had fewer review findings than stories that wrote tests after implementation.

**Evidence:** Story 3.4 (AiProvider — test-first) had 1 minor review finding. Story 3.7 (large-paste — tests after implementation) had 3 BLOCKERs.

**Action:** Encourage test-first for all future stories, especially for connective/cross-cutting logic.

### Epic 4: Branching (Sibling Under Same Parent, Branch-Aware Edit, Regenerate Within Branch)

**Stories:**
- 4.1: Branch Creation — Sibling under same parent, new conversation sharing rootConversationId
- 4.2: Edit Continues from Most-Recent Sibling — branch-aware edit targeting
- 4.3: Regenerate Within a Branch — reuses 3.6's same-ID overwrite inside branched conversations

**Dependencies on Epic 3:**
- E3.1 (Entities + Repos): `Message.parentId` self-relation, `Conversation.rootConversationId` — must be solid
- E3.2 (ConversationService): `getById` with ownership check reused by branch lookup
- E3.3 (ChatService): Already depends on `MessageRepository.findByConversation` — branch-aware querying extends this
- E3.5 (MessageService.editLatest): Must be branch-aware — edit targets most-recent sibling in active branch
- E3.6 (ChatService.regenerate): Reused by 4.3 — no new streaming logic needed

**Risks:**
1. Branch-aware queries: `findLatestUserMessage` must filter by active branch lineage (not the whole conversation). This is the trickiest part of Epic 4 — get it wrong and edits affect wrong messages.
2. RootConversationId propagation: When a branch creates a new conversation, the `rootConversationId` must be copied from the parent. Edge cases: branching from a branch, branching from a branched assistant message.
3. UI integration: Branching is invisible without a branch-aware sidebar (Epic 6). Epic 4 stories will need route handler wiring but no UI changes.

**Total Stories:** 3
